## Slide 4: 午後の重要テクノロジー略語ガイド

午後の難関トピックで頻出する 4 大キーワード（RAG・CoT・ReAct・Agent）の直感理解

| 略語 / 正式名称 | 日本語ワンフレーズ解説（直感理解） | ここを押さえる！（試験・実務ポイント） |
|---|---|---|
| RAG（Retrieval-Augmented Generation） | 社内資料を検索して回答に引用させる技術 | モデルの再学習なしに最新・独自情報に対応し、ハルシネーションを防止 |
| CoT（Chain-of-Thought） | 段階的に考えさせて推論ミスを防ぐ指示技法 | 「ステップ順に考えて」と促すプロンプト。複雑な計算や論理思考で精度向上 |
| ReAct（Reasoning + Acting） | 思考とツール実行を交互に繰り返し目標を達成する仕組み | 「考える→検索/ API 実行→結果を確認」の自律ループで動くエージェントの基本構造 |
| Agent Search（Grounding & Vector Search） | Google 検索基盤と直結し出典付き回答を自動化するサービス | 自前で検索パイプラインを作らずに高精度 RAG を実現 |

★ 午後の攻略ポイント（見分け方のコツ）
午後は「モデル単体で解く技術（CoT）」と「外部ツールや DB と連携する技術（RAG / ReAct / Agent）」の境界線が頻出です。迷ったら「外部へアクセスしているか？」を判断軸にしましょう。

## Slide 29: AI エージェントの主要な 2 大モデルと実行サイクル

エージェントの仕組み: 会話型とワークフロー型
意図を理解して意味ある回答を返す「会話エージェント」と、業務プロセスを自律的に遂行する「ワークフロー エージェント」。いずれのエージェントも「入力 ➔ 理解 ➔ ツール呼出 ➔ 生成 ➔ 返却」の 5 ステージを経てタスクを完了します。

| ステージ | 会話エージェント（言葉の字面だけでなく背後にある意味や意図を理解し、文脈に沿った自然で価値の高い回答を生成） | ワークフロー エージェント（複雑な一連のプロセスを案内・代行し、作業を正確かつ自律的に遂行・合理化） |
|---|---|---|
| 1 入力 | ユーザーが入力を提供: メッセージを入力するか、音声で直接話しかける | タスク定義 / トリガー: フォーム送信、ファイル配置、定期スケジュール等で開始 |
| 2 理解 | エージェントが理解する: 高度な AI で発話の背後にある本質的な意図を解釈 | エージェントが理解する: 要件を解釈し、達成に必要な一連の自動化手順を定義 |
| 3 ツール呼出 | ツールを呼び出す: Web検索・社内DB・外部アプリ等で必要情報を収集 | ツールを呼び出す: データ変換、ファイル転送、通知送信、外部API呼出 |
| 4 生成 | 回答を生成する: ユーザーのリクエストに即した自然で正確な回答文を構成 | 結果・出力を生成する: レポート作成、データファイル出力、ステータス更新 |
| 5 返却 | 回答を返す: 画面へのテキスト表示または音声でユーザーへ提供 | 結果・出力を返す: メール通知、DB反映、ダッシュボード配信、ストレージ保存 |
| 例 | 質問への回答 / 気軽なチャット / 情報へのアクセス | e コマース注文処理 / 顧客オンボーディング / 自動調査（Deep Research） / セキュリティログ解析 |

ポイント: 会話エージェントは「ユーザー対話の最適化」、ワークフロー エージェントは「組織プロセスの自律遂行」に強みを発揮

## Slide 99: トークン単位の定義と課金イメージ

トークン（Token）とは？
AI がテキストを処理する際の「基本分割単位」です。人間が認識する文字や単語とは異なります。
英語では 1 単語が約 1.3 トークン、日本語では 1 文字が約 1〜2 トークン（漢字や平仮名で変動）として計算されます。

視覚的イメージ: テキストのトークン分割
- 元の日本語テキスト: 「自然言語処理された断片」
- 分割結果: [自然言語] [処理] [細分化] [された] [断片]（それぞれの断片（トークン）ごとに処理・課金される）
- API 利用料金の計算: 計 5 トークン として課金

## Slide 110: 意思決定: さまざまな企業とモデルの比較

要素の慎重な精査と客観的リソースの徹底調査により、ニーズに最も合致した費用対効果の高いソリューションを選択

**01 さまざまな企業とモデルの比較**（検討の 4 つの側面）— 複数の提供元やモデルを用途に合わせて横断的に見回り、品質・コスト・制約条件を多角的に評価します。

- 追加費用を考慮に入れる: データ保管、API 呼出頻度、ファインチューニングなどの付随コストを網羅
- 注意事項・利用規約を読む: 使用量上限（クォータ）、データプライバシー保護、各種コンプライアンス規約を確認

**02 比較のための主なリソース**（情報収集の 3 大ソース）— 正確で偏りのない判断を下すために、一次情報・独立評価・実運用コミュニティの知見を活用します。
- プロバイダのウェブサイト（一次情報）: 各企業の公式料金ページ、最新の利用規約、公式仕様ドキュメントを直接確認して最新の価格体系と上限を把握
- 研究論文とベンチマーク（中立評価）: 各モデルの客観的・第三者による性能評価レポートや学術論文を参照し、公称値に惑わされない実力を検証
- コミュニティ フォーラムと議論（実務事例）: 他のユーザーや導入エキスパートと交流し、実際の運用ノウハウ、障害時の挙動、隠れた運用コストなどの実情を収集

ベストプラクティス: 01 の 4 項目を 02 の信頼できるリソースで照合・精査することで、確実で費用対効果の高いモデル採用を実現

## Slide 134: モジュール 03：試験出題ポイントチェックリスト

生成 AI スタック階層・自律型エージェント設計・トークンコスト最適化の頻出論点整理

**① 5 つのレイヤ構造**
- インフラ〜モデル層: TPU/GPU ハードウェアと Gemini 基盤モデルの明確な分離。
- プラットフォーム（Agent Platform）: 検索・チューニング・評価ツール群を提供する開発環境層。
- エージェント〜アプリ層: タスク実行オーケストレーションとユーザー向け UI / 業務機能。
- ★試験のツボ: 要件（例: 監査要件や独自 UI 構築）に対し、どのレイヤの技術を選択すべきかを問う問題が頻出。

**② エージェントとモデル**
- モデル単体の役割: 入力コンテキストに基づくテキスト・コードの「推論と生成エンジン」。
- エージェントの本質: 目標達成に向けた「推論＋計画＋外部ツール（API）呼び出し」。
- 自律的なタスク遂行: 実行結果を観察（Observe）し、完了までループ実行する自律性。
- ★試験のツボ: 「受動的な回答生成」か「外部 DB 更新・予約等のアクション実行」かでモデルとエージェントを区別。

**③ トークン課金とリソース**
- 入出力トークンの非対称性: 一般に出力（生成）トークンの方が処理負荷が高く単価も高額。
- コンテキストウィンドウ管理: 長大入力は情報保持に優れるが、レイテンシと課金増のトレードオフ。
- クォータとスループット: RPM/TPM 制限の管理や、安定稼働に向けたプロビジョンド割当。
- ★試験のツボ: コスト削減策として「不要なプロンプトの削減」や「キャッシュ活用（Context Caching）」が直結。

### 1. Stack 5 lớp của Gen AI (生成 AI の 5 層) và "ai chịu trách nhiệm lớp nào"

| Lớp | Vai trò | Ví dụ Google Cloud | Người phụ trách (slide 93-95) |
|---|---|---|---|
| Application | Giao diện người dùng | Gemini app, Google Workspace with Gemini, NotebookLM | Business leader (ビジネス リーダー) |
| Agent | Đạt mục tiêu bằng reasoning + tool | Agents xây trên Agent Platform / AI Applications (Agentspace nay thuộc Gemini Enterprise) | Developer (デベロッパー) |
| Platform | API, quản lý dữ liệu, deploy model, MLOps | Agent Platform (trước đây là Vertex AI; deck dùng tên mới) | AI practitioner (AI 担当者) |
| Model | "Bộ não" | Gemini, Imagen, Veo, Chirp, Gemma, Claude, Llama (qua Model Garden) | AI practitioner |
| Infrastructure | Tính toán, lưu trữ, mạng | TPU, GPU, AI Hypercomputer | AI practitioner |

Hay nhầm: Developer = xây agent / tích hợp AI vào app (đáp án slide 122); AI practitioner = customize / deploy / tối ưu model + responsible AI (đáp án slide 116). Business leader chỉ DÙNG giải pháp dựng sẵn.

### 2. Model vs Agent vs Application

- Model: engine suy luận và sinh nội dung, thụ động (nhận prompt, trả output).
- Agent = model + reasoning loop + tools: quan sát (observe) - suy nghĩ (reason) - hành động (act) lặp lại tới khi đạt mục tiêu. Điểm khác biệt với model đơn lẻ là "reasoning loop và tools" (đáp án slide 128).
- Application cung cấp UI và mục tiêu tổng thể; agent là thành phần thông minh bên trong (slide 40). Multi-agent: nhiều agent chuyên biệt phối hợp trong một app.
- Conversational agent (hỏi đáp, chat) vs Workflow agent (tự động hóa quy trình: xử lý đơn hàng, onboarding, phân tích log bảo mật). Cùng chu trình 5 bước: input - hiểu - gọi tool - tạo output - trả kết quả.
- Kỹ thuật prompt/reasoning: CoT (chỉ suy luận trong model, không truy cập ngoài), ReAct (suy luận + hành động xen kẽ, dùng tool), RAG (truy xuất tài liệu ngoài để grounding, giảm hallucination mà không cần retrain). Mẹo của deck: "có truy cập bên ngoài không?".

### 3. Model Garden vs AutoML vs Custom training (câu hỏi rất hay ra)

| Nhu cầu | Chọn |
|---|---|
| Cần model sẵn, hiệu năng tốt, nhanh, chi phí vừa (dịch, tóm tắt, ...) | Model Garden (model có sẵn / pre-trained API, có thể fine-tune) |
| Có dữ liệu riêng, ít chuyên môn ML, muốn no-code/low-code | AutoML |
| Nhà nghiên cứu cần kiểm soát hoàn toàn kiến trúc và quy trình training (vd dự đoán gấp cuộn protein) | Custom training (framework tự chọn, TPU/GPU) |
| Chỉ cần soạn nháp nội dung nhanh (mô tả sản phẩm) | Ứng dụng gen AI dựng sẵn như Workspace with Gemini (đáp án slide 124), không cần build model |

Nguyên tắc: bắt đầu từ giải pháp có sẵn, chỉ customize khi thật sự cần (customize nhiều = tốn thời gian, tiền, nhân lực).

### 4. MLOps trên Agent Platform: chọn công cụ theo tình huống

| Tình huống | Công cụ |
|---|---|
| Quản lý phiên bản model, theo dõi thay đổi | Model Registry |
| Model đã deploy bị giảm hiệu năng, cần tìm nguyên nhân / retrain | Model Monitoring (phát hiện training-serving skew và drift) |
| Tự động hóa pipeline từ tiền xử lý dữ liệu đến deploy | Workflow orchestration (Agent Platform Pipelines) |
| Chia sẻ / tái sử dụng feature ML | Feature Store |
| So sánh hiệu năng model | Model evaluation |

Hay nhầm: skew = chênh lệch giữa dữ liệu train và dữ liệu lúc phục vụ; drift = dữ liệu đầu vào thay đổi theo thời gian.

### 5. Hạ tầng và Edge AI

- GPU: bộ xử lý song song đa dụng; TPU: chip do Google thiết kế riêng cho workload ML/AI (tối ưu phép toán ma trận). Cả hai là bộ xử lý chuyên dụng cho xử lý song song (đáp án slide 77).
- Storage hiệu năng cao: lưu dataset lớn và truy cập nhanh để GPU/TPU không bị nghẽn.
- Edge computing: chạy AI gần nguồn dữ liệu. Lợi ích: phản hồi real-time / độ trễ thấp, bảo mật riêng tư, ít phụ thuộc internet (đáp án slide 130). Đánh đổi: tài nguyên thiết bị hạn chế.
- Gemini Nano: model nhỏ chạy on-device (Pixel, Android qua AI Edge SDK). Gemini Pro/Flash/Ultra thường chạy trên cloud. LiteRT (tên mới của TensorFlow Lite): runtime chạy model ML trên thiết bị edge/di động.

### 6. Chi phí, token, quota

| Mô hình tính phí | Ý nghĩa |
|---|---|
| Pay-as-you-go (従量制) | Theo token / ký tự đã xử lý |
| Subscription | Phí định kỳ, giới hạn theo usage hoặc tính năng |
| License | Phí một lần hoặc định kỳ, dùng thương mại/nhúng sản phẩm |
| Free tier | Miễn phí có giới hạn, để thử nghiệm / phi thương mại |

- Ba hoạt động tốn tiền khi xây giải pháp: training, deploy lên endpoint, và dự đoán (inference). Training/deploy tính theo thời gian compute và dung lượng lưu trữ.
- Yếu tố ảnh hưởng chi phí: kích thước/độ phức tạp model, context window, tính năng đặc biệt, deploy.
- Token output thường đắt hơn token input; context window dài làm tăng chi phí và độ trễ. Cách giảm chi phí: rút gọn prompt, caching (Context Caching), chọn model nhỏ hơn đủ dùng (vd Flash thay vì Pro), batch.
- Quota/rate limit (RPM, TPM) và Provisioned Throughput (băng thông dành riêng, ổn định cho production): phải lập kế hoạch dung lượng (capacity planning). (Tên gọi cụ thể có thể thay đổi theo thời kỳ, chưa chắc.)
- Công cụ: Google Cloud Pricing Calculator để ước tính chi phí.

### 7. Khung quyết định và vận hành (domain business strategy)

- Quy mô nhỏ: dùng công cụ dựng sẵn; quy mô lớn: ưu tiên scalability, security, và chú ý chi phí hạ tầng, lưu trữ, latency.
- Cân nhắc khác: UI/UX, quyền riêng tư (data security + compliance), latency, kết nối/offline, độ chính xác, khả năng giải thích (explainability, đặc biệt y tế/tài chính).
- So sánh nhà cung cấp: kiểm tra tính năng, bảng giá, chi phí phát sinh, điều khoản (quota, privacy, compliance); đối chiếu bằng website nhà cung cấp, paper/benchmark, cộng đồng.
- Bảo trì: monitoring và retrain định kỳ, cập nhật dữ liệu, patch phần mềm, hạ tầng, bảo mật và compliance liên tục. Không được "ưu tiên triển khai nhanh, bỏ qua governance/maintenance" (đáp án sai ở slide 132).

### 8. Câu hỏi luyện tập (kiểu đề thi)

1. Công ty cần chatbot trả lời dựa trên tài liệu nội bộ, cập nhật thường xuyên, không muốn retrain model. Giải pháp phù hợp nhất? -> RAG / grounding (không phải fine-tune hay train mới).
2. Một nhóm cần model phát hiện bất thường trên dữ liệu bảng, không có chuyên gia ML. Chọn gì? -> AutoML trên Agent Platform.
3. Điểm khác biệt chính giữa agent và model đứng riêng? -> Agent có reasoning loop và tools để hành động đạt mục tiêu; model chỉ sinh output.
4. Model đã deploy, độ chính xác giảm dần do dữ liệu thực tế đổi. Công cụ nào trước tiên? -> Model Monitoring (phát hiện drift/skew), sau đó retrain qua pipeline.
5. Ứng dụng cần chạy AI trên điện thoại khi offline và dữ liệu không rời thiết bị? -> Edge AI với Gemini Nano (LiteRT để chạy model).
6. Muốn giảm chi phí gọi API gen AI? -> Rút gọn prompt không cần thiết, dùng Context Caching, chọn model nhỏ phù hợp (không phải tăng context window).
